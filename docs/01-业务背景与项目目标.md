# PulseCart 业务背景与项目目标

## 1. 文档定位

PulseCart 是品牌或电商公司内部使用的商品体验问题管理平台。平台把分散在订单系统、客服系统和电商平台中的商品评论，转化为可追溯、可复核、可分派、可验证的问题线索。

本文回答四个问题：

1. 为什么需要 PulseCart；
2. 谁使用 PulseCart，以及他们要完成什么工作；
3. PulseCart 如何形成从评论到问题关闭的业务闭环；
4. 当前版本做到什么程度，后续如何演进。

本文中的“当前已实现”以仓库代码和本地验证结果为准，不把历史实验代码或规划能力描述成生产能力。

## 2. 行业背景与业务痛点

### 2.1 评论多，但问题发现慢

品牌和电商团队每天都会收到商品评价。评论数量增长后，人工逐条阅读无法覆盖全部数据，简单查看好评率又无法回答“用户究竟在抱怨什么”。例如，同一个 SKU 的差评可能分别来自噪音、导航、清洁效果、包装破损和售后响应，问题优先级并不相同。

### 2.2 情感分类结果不能直接指导业务

“正面、 中性、负面”只描述态度，不描述责任对象和行动方向。运营需要知道负面评价集中在哪个体验属性、哪个产品版本、哪个渠道和哪个时间段，并能回看原文证据。

### 2.3 数据和模型缺少可追溯性

如果没有数据集版本、原始文件校验和、字段映射、模型版本、训练样本和随机种子，模型指标无法复现；如果人工修正没有留下审核人和时间，团队也无法判断标签质量。

### 2.4 发现问题后没有处置闭环

单纯的可视化页面不能保证问题被处理。真正有业务价值的系统需要将洞察转成问题卡，分派负责人，记录处置过程，要求验证结果，并在关闭时保留来源评论和解决说明。

## 3. 产品定位

### 3.1 一句话定位

> PulseCart 是品牌或电商公司的内部商品体验问题管理平台，帮助商品团队从评论中发现问题、组织复核、分派处理并验证关闭。

### 3.2 产品边界

PulseCart 负责：

- 评论数据导入、字段标准化和质量报告；
- 数据集版本管理和原始评论证据保存；
- 人工审核任务分发和审核标签沉淀；
- 情感与体验属性分析的任务编排；
- 商品体验问题卡的创建、分派、处理和关闭验证；
- 模型训练运行、评测记录和模型发布门槛。

PulseCart 不负责：

- 直接抓取需要登录的电商平台数据；
- 保存消费者姓名、手机号、地址等身份信息；
- 自动替商品团队做最终质量判定或赔付决策；
- 在没有真实训练和独立评测依据时宣称 BERT 已达到生产效果；
- 把合成演示数据的结果解释为真实电商泛化能力。

## 4. 目标用户与业务价值

| 用户角色 | 主要任务 | PulseCart 提供的价值 |
| --- | --- | --- |
| 商品运营 | 找出某个 SKU 当前最严重的体验问题 | 负面趋势、属性分布、证据评论和问题卡 |
| 品类负责人 | 比较商品、版本和渠道差异 | 统一数据口径和可追溯的对比结果 |
| 客服/售后负责人 | 识别集中投诉并推动处理 | 负面线索、问题严重度和负责人协同 |
| 数据分析师 | 校验数据质量和模型效果 | 导入报告、审核样本、评测指标和数据指纹 |
| 算法工程师 | 训练、评估、压缩和发布模型 | 独立 NLP 服务、训练任务和模型注册信息 |
| 质量/研发人员 | 处理具体商品体验问题 | 问题卡状态机、来源评论和关闭验证 |
| 管理者 | 了解问题规模和处理进度 | 按周期、SKU、属性和状态的汇总视图 |

## 5. 典型业务场景

### 场景 A：新商品上市后的体验监控

商品运营导入上市后的评论，系统校验数据并生成版本化数据集。运营查看负面评论较多的属性，回查代表性评论，确认“导航避障”是否是需要研发介入的问题。

### 场景 B：产品版本改版后的效果验证

品类负责人按 `product_version` 和时间窗口比较改版前后的负面比例。系统结果必须带数据集版本、模型版本和筛选条件，避免不同口径的报表被误认为改版效果。

### 场景 C：模型上线前的人工质量控制

分析师从低置信度、负面预测和高风险属性中抽样。运营确认情感和属性标签，分析师复核部分样本，只有使用 `approved` 或 `verified` 标签的数据才允许提交训练任务。

### 场景 D：问题从发现到关闭

运营创建“回充失败”问题卡，指定处理人；研发处理后将状态推进到 `pending_validation`；运营回查新一批评论并填写验证说明，确认后关闭问题卡。

## 6. 核心业务闭环

```text
合规评论 CSV
    -> 字段映射和质量校验
    -> 生成不可变 dataset_version 与 SHA-256
    -> 规范化评论记录
    -> 分层抽样和人工审核
    -> 只使用已审核标签训练/评测模型
    -> 按 SKU、版本、渠道、属性聚合体验问题
    -> 创建问题卡并分派负责人
    -> 处理、验证、关闭
    -> 结果回流到下一轮数据和模型质量改进
```

其中最关键的控制点是：

- 导入失败的行不能进入分析数据集；
- `synthetic_reference` 只能作为演示参考标签，不能直接成为训练标签；
- 训练任务必须携带数据集版本和模型版本；
- 问题卡的来源评论必须属于同一数据集版本；
- 关闭问题必须经过 `pending_validation`，不能从 `open` 直接关闭。

## 7. 当前版本基线

### 7.1 已实现并完成本地验证

- 1,200 条扫地机器人合成评论可重复导入；
- 300 条固定人工审核任务可幂等初始化；
- CSV 必填字段、日期、评分、空文本、重复 ID、文本长度和语言标记校验；
- 数据集版本、原始文件 SHA-256、有效行、拒绝行和拒绝原因记录；
- 管理员登录、审核任务读取和人工审核结果保存；
- 后端读取已审核记录并调用独立 NLP 训练服务；
- 训练结果回写 MySQL，包含训练/测试样本数、Accuracy、Macro-F1 等信息；
- 商品体验问题卡状态流转：`open -> in_progress -> pending_validation -> closed`。

### 7.2 已实现但当前属于降级或实验状态

- 当前真实训练仅使用 15 条人工审核样本，其中 12 条训练、3 条测试；
- 当前实测 Accuracy 为 `0.333333`，Macro-F1 为 `0.222222`；
- 因样本不足且未达到发布门槛，模型状态为 `evaluation_only`，不能作为上线模型；
- 旧的单条分析、关键词、模型等页面仍保留为实验对比入口，不能等同于完整的运营分析链路；
- Redis、对象存储和大规模异步任务是架构目标，当前 P1 主要使用本地文件和同步编排。

### 7.3 历史实验资产

原项目中的 BERT/RoBERTa 微调、BiLSTM + Attention、属性级情感分析、模型压缩、蒸馏、量化和模型 API 设计仍有保留价值，适合作为模型实验与演进路线。它们需要在有足量人工标注、独立测试集和实测基准后再进入默认分析链路。

## 8. 量化目标与验收口径

以下是产品目标，不是当前已达成指标：

| 指标 | 目标口径 | 当前状态 |
| --- | --- | --- |
| 导入可追溯率 | 每个数据集都有版本、文件指纹和质量报告 | P1 已实现 |
| 重复导入一致性 | 同一文件和映射返回同一版本 | P1 已实现 |
| 审核训练隔离 | 未审核标签进入训练集的数量为 0 | P1 已实现 |
| 训练发布门槛 | Macro-F1 >= 0.65 且独立测试样本 >= 30 | 规则已实现，当前未达标 |
| 证据可回查率 | 每条业务洞察都能定位到原始评论 | P2/P3 目标 |
| 问题关闭完整率 | 关闭前必须有验证说明和来源证据 | 状态机已实现，需持续补测试 |
| 业务响应效率 | 从导入到发现首个高风险问题的时间可测 | 待接入真实分析聚合 |

## 9. 产品路线

| 阶段 | 重点交付 | 完成定义 |
| --- | --- | --- |
| P1 数据闭环 | 导入、校验、版本化、审核、问题卡 | 演示数据可完整走通且可复查 |
| P2 分析闭环 | 批量情感、属性、主题聚合和证据查询 | 看板结论均有版本和原文来源 |
| P3 运营闭环 | 趋势、告警、导出、负责人和改版对比 | 发现的问题可以进入团队日常流程 |
| P4 工程交付 | 异步 worker、Redis、对象存储、迁移和集成测试 | 新环境可以按文档独立启动 |
| P5 模型演进 | Transformer、蒸馏、量化和模型灰度 | 新模型在独立评测达标后可回滚发布 |

## 10. 简历项目表述边界

推荐表述：

> PulseCart 商品体验问题管理平台：面向品牌和电商商品运营场景，基于 Vue 3、FastAPI、MySQL 构建评论数据版本化、人工审核、可复现情感训练和问题卡闭环；实现 CSV 质量校验、数据指纹、独立 NLP 训练服务编排、模型发布门槛和问题关闭验证。

必须使用仓库中真实运行产出的指标，不能写“真实生产上线”“海量实时分析”或未经独立评测证明的“BERT 准确率”。
