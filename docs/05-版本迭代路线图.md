# PulseCart 版本迭代路线图

> 当前基线：P1 原型（GitHub `main`）  
> 回退基线：`pulsecart-original`  
> 迭代原则：保留 JeecgBoot 的登录、权限、路由和后台能力；逐步将 PulseCart 打造成独立的商品体验运营工作台，不进行框架级重写。

## 1. 当前基线与目标

当前 P1 已具备可演示的业务闭环：评论数据导入、审核任务生成与提交、受控模型训练、评测发布门槛和问题卡状态流转。前端入口为 `jeecgboot-vue3/src/views/sentiment/operations/index.vue`，业务 API 位于 `jeecg-fastapi/app/api/pulsecart.py`，模型能力位于 `sentiment-ai/`。

下一阶段不是增加更多页面，而是先让现有工作台在真实操作中稳定、清楚、可追溯。所有迭代必须围绕下列结果：

1. 每次用户操作只得到一次、语义明确的反馈。
2. 任何会改变业务状态的操作都不能因重复点击产生重复数据或冲突状态。
3. 审核、问题处置和模型判断都有足够证据可回查。
4. 新功能不破坏 P1 已验证的导入、训练、模型门槛和问题卡闭环。

## 2. 版本总览

| 版本 | 名称 | 核心目标 | 完成后用户可以做到 | 不在本版本做 |
| --- | --- | --- | --- | --- |
| `v1.1` | 稳定工作台 | 消除重复反馈、重复提交和页面状态混乱 | 稳定完成导入、审核、训练、问题卡处置 | 替换 Vue/Jeecg 框架、重建所有页面 |
| `v1.2` | 审核与证据 | 让审核队列成为可独立完成的工作流 | 依据原始评论审核，查看理由与历史 | 自动标注替代人工审核 |
| `v1.3` | 问题管理 | 将问题卡升级为可跟踪、可验证的运营事项 | 分配负责人、设置优先级和截止时间，回看证据 | 对外通知、复杂项目管理系统 |
| `v1.4` | 专属产品外壳 | 形成 PulseCart 的专属信息架构和导航 | 在总览、审核、问题、模型数据间高效切换 | 改用 React/Next/Nuxt 或拆分为新前端工程 |

版本必须按顺序合入 `main`。允许在同一版本内拆分多个短分支，但后序版本不可依赖未合入的前序任务。

## 3. 交付与分支规则

### 3.1 受保护基线

| 分支 | 用途 | 操作规则 |
| --- | --- | --- |
| `main` | 当前可运行的 PulseCart 基线 | 只合入已通过验证的版本任务 |
| `pulsecart-original` | 优化前回退点 | 永不直接开发或重写历史 |
| `feat/pulsecart-vX.Y-*` | 单个迭代任务分支 | 从最新 `main` 创建，完成后合回 `main` |

每项工作开始前先同步 `main`，禁止把本机运行目录、真实导入数据、模型产物、日志或本地 `.env` 文件提交到 Git。根目录 `.gitignore` 已排除这些内容。

### 3.2 每项任务的最小交付

一个独立任务窗口只处理一张任务卡，并在完成时提供：

1. 实现说明：解决了什么、没有改变什么。
2. 文件清单：新增或修改的前后端、测试、文档文件。
3. 验收结果：逐条对应任务卡的验收标准。
4. 验证记录：至少包含相关自动化测试或前端生产构建。
5. Git 状态：工作区是否干净、提交哈希、是否已推送。

除非任务卡明确要求，不能顺带重构无关的 Jeecg 系统模块、替换依赖版本或重做全局视觉主题。

### 3.3 通用质量门槛

合入 `main` 前按影响范围执行：

| 变更类型 | 必须验证 |
| --- | --- |
| Vue 页面、API 调用、路由或样式 | `jeecgboot-vue3` 中执行 `npm run build` |
| FastAPI 领域接口、数据库状态机 | `jeecg-fastapi/scripts/test_pulsecart_domain.py` 与对应单元/集成测试 |
| NLP 导入、训练、模型发布规则 | `sentiment-ai/tests/` 中受影响的测试；必要时运行固定演示数据闭环 |
| 数据库结构或接口契约 | SQL 迁移可重复执行，接口契约文档同步更新 |

当前 `vue-tsc --noEmit` 受本机 Node 22 与已安装工具版本不兼容影响，不能作为该仓库的通过门槛；前端以成功的 `npm run build` 为准，工具兼容性修复应另立任务。

## 4. v1.1 稳定工作台

### v1.1-A 操作反馈治理

**目标**：任何单次用户动作只显示一次反馈；后台加载、轮询、刷新和退出登录不显示“操作成功”。

**现状**：全局 HTTP 成功提示已调整为默认静默；PulseCart 操作页使用统一提示键。但应在全站关键操作和失败分支中完成一致性审计，避免局部页面直接触发重复 `message.success`。

**主要范围**：

- `jeecgboot-vue3/src/utils/http/axios/index.ts`
- `jeecgboot-vue3/src/api/sys/user.ts`
- `jeecgboot-vue3/src/views/sentiment/operations/index.vue`
- 由实际调用链确认的 PulseCart API 与组件

**验收标准**：

1. 导入、创建演示数据、提交审核、发起训练、同步模型、更新问题卡各只出现一条语义化反馈。
2. 快速连续触发不同操作时，旧提示不会在屏幕上堆叠。
3. 页面初始加载、手动刷新、轮询、退出登录不会出现成功提示。
4. 后端业务失败仍显示可理解的错误信息，且不与页面错误提示重复。

**依赖**：无，可作为第一个独立任务执行。

### v1.1-B 变更操作防重复

**目标**：避免重复点击或网络慢导致重复导入、重复审核、重复训练、重复状态流转。

**主要范围**：

- PulseCart 工作台中的导入、演示数据、审核、训练、模型同步、问题卡操作按钮
- 必要时的 FastAPI 幂等性/冲突响应
- 相关前后端测试

**实施要求**：

1. 前端在请求进行时锁定对应动作，仅影响当前动作，不阻塞无关浏览操作。
2. 请求结束后无论成功或失败都恢复可用状态。
3. 后端对会创建记录或切换状态的接口维持幂等性或返回明确的冲突结果。
4. 不以纯前端禁用按钮替代后端防护。

**验收标准**：

1. 连续点击提交审核只形成一次审核结果。
2. 同一训练版本不能被重复创建；重复请求返回可解释结果。
3. 同一问题卡状态迁移不会因重复请求产生非法历史。
4. 慢请求期间按钮状态、加载状态和结束后的状态正确。

**依赖**：建议在 `v1.1-A` 完成后执行，以便为成功、冲突、失败分别提供唯一反馈。

### v1.1-C 页面状态统一

**目标**：工作台的加载、空数据、错误和可恢复状态清晰一致，避免用户把“正在加载”误判为“没有数据”。

**主要范围**：

- `jeecgboot-vue3/src/views/sentiment/operations/index.vue`
- 可复用的 PulseCart 页面状态组件或局部组合式函数
- 接口失败重试逻辑

**验收标准**：

1. 首次进入、筛选刷新和操作后刷新都有明确加载反馈。
2. 没有任务、没有问题卡、没有运行记录时显示说明性空状态和下一步动作。
3. 请求失败时显示错误原因与重试入口，不能只留下空白表格。
4. 重试成功后页面能恢复，无需浏览器整页刷新。
5. 手机宽度与桌面宽度下文字、按钮、表格不发生遮挡。

**依赖**：可与 `v1.1-B` 并行；合入前需要解决两者共同改动的状态管理冲突。

### v1.1-D 审核队列可读性

**目标**：让审核人员首先看到最值得处理的评论，而不是从长表格中寻找线索。

**主要范围**：

- 审核任务接口返回的置信度、预测情感、属性、风险信息
- 审核表格列、默认排序、优先级标识和筛选

**优先级建议**：负向预测、低置信度、高影响属性（可靠性、售后、导航避障）优先；剩余样本保持分层随机抽样，不能使审核集失去代表性。

**验收标准**：

1. 每条任务能一眼看到预测情感、置信度、关联属性和优先级原因。
2. 默认排序符合“高风险优先”，同时能切换为抽样/时间顺序。
3. 审核进度使用全量任务数作为分母，不因当前筛选而失真。
4. 审核行为和现有训练数据契约兼容。

**依赖**：`v1.1-C`，因为需要使用稳定的加载、空状态和错误状态。

### v1.1 版本完成定义

1. `v1.1-A` 至 `v1.1-D` 全部通过各自验收。
2. 使用固定 1,200 条合成评论完成一次导入、审核、训练与问题卡处置，无重复记录或重复提示。
3. 前端 `npm run build` 成功，受影响后端/NLP 测试成功。
4. 形成一次版本提交并在 GitHub `main` 可回溯。

## 5. v1.2 审核与证据

### v1.2-A 独立审核队列

将审核从综合工作台拆分为聚焦的“审核队列”页面，但保留工作台中的待审数量与快捷入口。页面应支持优先级、情感、属性、产品、时间窗口筛选和上一条/下一条连续审核。

**验收标准**：审核人员无需复制 `review_id`，可在一个连续流程中完成多条任务；离开后能回到原筛选位置。

### v1.2-B 原始证据与审核理由

每个审核任务展示原始评论、预测结果、模型版本、数据集版本和必要上下文。审核提交应支持受控理由标签和可选备注，不允许修改原始评论。

**验收标准**：任一已审核记录都能追溯“谁在何时基于什么证据做了什么修正”。

### v1.2-C 审核历史与二次复核

保留审核版本和冲突历史，支持按规则抽取二次复核任务。分歧不覆盖原记录，而是作为质量数据进入报告。

**验收标准**：可以统计复核覆盖率、审核一致性和分歧原因；训练只使用被规则允许的标签版本。

### v1.2 版本完成定义

审核人员可从队列进入、查看证据、提交标签和理由、完成连续审核；数据分析人员可追溯历史并识别复核分歧。

## 6. v1.3 产品问题管理

### v1.3-A 问题看板与字段补齐

将问题卡以列表和看板两种视图呈现，补充严重度、负责人、截止日期、来源属性、受影响商品和状态。

**验收标准**：运营负责人能按状态、负责人、严重度和逾期情况扫描问题，而不必逐条打开卡片。

### v1.3-B 证据关联与处置历史

问题卡必须关联来源评论、聚合指标或趋势证据；每次状态、负责人、严重度变更保留历史记录。

**验收标准**：打开一张问题卡即可回答“为什么创建、由谁处理、发生过什么变化、依据是什么”。

### v1.3-C 验证闭环与 SLA

在 `pending_validation` 状态记录验证窗口、验证结果和佐证；计算临近到期和已逾期状态，但不自动向外部系统发送通知。

**验收标准**：关闭问题卡前必须填写验证结果或明确的关闭理由；状态流转与 P1 既有规则保持兼容。

### v1.3 版本完成定义

一个问题能从评论证据创建，分配给负责人，经处置和验证后关闭，并完整保留状态与证据链。

## 7. v1.4 PulseCart 专属产品外壳

### v1.4-A 专属导航与信息架构

在保留 Jeecg 登录、权限、路由守卫和后台 API 能力的前提下，提供 PulseCart 一级导航：总览、审核队列、问题、模型与数据。系统管理项不混入运营主流程。

**验收标准**：运营用户进入产品后能在两次点击内抵达四个核心工作区；无权限的入口不显示或给出清楚的权限说明。

### v1.4-B 总览页面

建立总览作为日常入口，呈现当前数据集、审核进度、待处理问题、模型健康与近期风险趋势；每个指标都可跳转到对应工作区和筛选结果。

**验收标准**：总览不只是静态大屏，每个数字都有数据窗口、数据集/模型版本和可继续操作的落点。

### v1.4-C 视觉系统收敛

形成可复用的 PulseCart 色彩、密度、表格、状态、空状态和图表规范。遵循现有 Vue/Ant Design Vue 组件体系，避免引入第二套 UI 框架。

**验收标准**：四个核心工作区在标题层级、操作区、状态色、表格密度和移动端响应上保持一致；不再出现全局样式覆盖导致的布局回归。

### v1.4 版本完成定义

PulseCart 对运营用户呈现为一个完整产品工作台，同时仍可复用 Jeecg 的认证、权限和工程基础。

## 8. 后续候选项（不进入 v1.1-v1.4）

下列事项有价值，但当前不应挤占稳定性和审核闭环的优先级：

- Redis worker、对象存储和大文件异步导入。
- 真实授权数据接入及数据脱敏流程。
- Transformer 微调、量化基准和模型灰度发布。
- 邮件、IM、工单系统等外部通知。
- 多租户、组织级权限和商业化计费。
- 迁移至 React、Next.js、Nuxt 或全新前端架构。

只有当 v1.4 的核心工作流稳定、用户角色和数据规模已明确时，才重新评估这些项的投入顺序。

## 9. 分窗口任务模板

将以下内容连同某一任务卡名称发送到独立窗口即可：

```text
在 PulseCart 仓库执行《docs/05-版本迭代路线图.md》中的 [任务卡名称]。

边界：只实现该任务卡及其必要测试/文档，不进行框架替换或无关重构。
开始前：检查当前 Git 状态和现有实现，保留用户已有变更。
完成条件：逐条满足任务卡验收标准，运行相关验证；说明修改文件、验证结果、未覆盖风险和 Git 状态。
提交要求：只在变更范围清晰、敏感配置与运行产物未被纳入时创建提交；不要强推、不要重置或覆盖既有工作。
```

建议执行顺序为：`v1.1-A` -> `v1.1-B` 与 `v1.1-C` -> `v1.1-D` -> `v1.2` -> `v1.3` -> `v1.4`。每完成一个版本，先完成一次完整的演示闭环和回归验证，再开启下一个版本。
