# PulseCart 详细设计说明书

## 1. 设计目标

PulseCart 的设计重点是“分析结果可信、业务动作可追踪、模型可以演进”。系统将业务 API 与 NLP 服务分离：业务后端负责身份、权限、数据版本、任务编排和问题卡；NLP 服务负责训练、评测、推理和模型产物。

当前设计以 P1 数据闭环为基线，P2/P3/P4 的异步分析、聚合看板、对象存储和告警在章节中明确标注。

## 2. 总体架构

```text
Vue 3 + JeecgBoot 工作台
          |
          | REST / JSON
          v
FastAPI 业务后端 :8006
  |-- 认证与系统权限
  |-- 数据集导入编排
  |-- 审核任务服务
  |-- 训练运行编排
  |-- 问题卡状态机
  |
  +--> MySQL 8: sys_* + pc_* 领域表
  +--> 本地运行目录 / MinIO: 原始文件、版本记录和模型产物
  +--> Redis 7 + worker: P4 异步任务
  |
  +--> NLP 训练服务 :8100
          |-- 数据预处理
          |-- TF-IDF + Logistic Regression 基线
          |-- BERT/RoBERTa 实验
          |-- 模型注册、评测和发布
          |-- 压缩/量化基准
```

### 2.1 组件职责

| 组件 | 职责 | 不能做的事 |
| --- | --- | --- |
| Vue 工作台 | 展示状态、提交表单、筛选数据 | 不在前端计算最终指标，不绕过权限 |
| FastAPI | 领域接口、事务、鉴权、审计和编排 | 不直接执行长时间模型训练 |
| MySQL | 结构化领域数据和状态 | 不存放大模型权重或大文件正文 |
| Redis/worker | 异步导入、批量分析、短期状态 | 不作为唯一事实来源 |
| 文件/MinIO | 原始 CSV、拒绝报告、模型产物 | 不替代数据库的状态记录 |
| NLP 服务 | 预处理、训练、评测、推理 | 不直接修改业务问题卡 |

## 3. 模块设计

### 3.1 数据集模块

入口位于业务后端的 `pulsecart.py` 和 `pulsecart_service.py`，底层复用 `sentiment-ai/app/services/dataset_import.py`。

处理步骤：

1. 校验扩展名、空文件和大小；
2. 读取字段映射；
3. 使用标准库 CSV 解析器读取内容；
4. 校验必填字段、日期、评分、重复 ID 和文本；
5. 对每个有效行做规范化；
6. 根据文件内容、映射和规则生成 `dataset_version`；
7. 计算文件 SHA-256；
8. 写入版本目录、原始快照和 MySQL；
9. 返回报告。

导入过程先完成解析和报告，再创建数据库记录。数据库提交失败时不应返回成功。重复版本通过唯一索引和版本查询实现幂等。

### 3.2 审核模块

演示任务由固定 JSONL 生成和初始化。真实产品中，抽样器应按以下策略组合：低置信度、负面预测、高风险属性、SKU/版本/渠道/月份/情感分层随机抽样。

审核只修改任务中的人工字段，不修改 `pc_review` 的原始文本。训练构建器以 `(dataset_version, review_id)` 关联任务与评论，防止跨版本复用同名评论 ID。

### 3.3 训练编排模块

业务后端在 `POST /analysis-runs` 中执行：

```text
检查 dataset_version
    -> 查询 approved/verified 任务
    -> 构建训练记录
    -> 校验人工标签和原文存在
    -> 调用 NLP POST /api/v1/training-runs
    -> 创建 pc_analysis_run(status=queued)
    -> 由 sync 接口查询 NLP 状态
    -> 回写 metrics、started_at、finished_at 和 error_message
```

训练请求包含数据集版本、模型版本、随机种子 `68` 和人工训练记录。NLP 服务返回 `queued/running/succeeded/failed` 四种状态。未知状态、错误 JSON、连接失败都不能写成成功。

### 3.4 模型与算法设计

#### 当前 P1 基线

- 文本输入：评论原文；
- 特征：字符级 TF-IDF；
- 分类器：Logistic Regression；
- 标签：`positive`、`neutral`、`negative`；
- 数据来源：仅 `approved` 和 `verified` 的人工标签；
- 评测：固定随机种子、训练/测试划分、Accuracy、Macro-F1、分类报告和混淆矩阵；
- 发布门槛：Macro-F1 >= 0.65，独立测试样本 >= 30。

字符级特征适合处理中文评论中的短语、错别字和产品术语，同时保留较好的可解释性，适合作为第一条可复现基线。

#### 历史资产的保留方式

| 能力 | 适合位置 | 接入前提 |
| --- | --- | --- |
| BERT/RoBERTa 微调 | P2 Transformer 实验 | 足量人工标签、独立评测集和资源预算 |
| BiLSTM + Attention | 算法对比实验 | 统一数据划分和指标 |
| 属性级情感分析 | P2 属性洞察 | 受控属性体系和属性级标注 |
| 蒸馏 | P5 小模型方案 | 教师模型达标且有蒸馏对比实验 |
| 动态 INT8 量化 | P5 部署优化 | 有压缩前后准确率、体积和延迟实测 |
| 模型 API | NLP 服务接口 | 健康检查、版本切换和回滚机制 |

这些资产不允许直接覆盖 P1 基线。每一个候选模型必须记录训练数据版本、代码版本、模型文件 SHA-256、指标和资源消耗。

### 3.5 问题卡模块

问题卡在 `pc_issue` 保存业务事实，来源评论 ID 以 JSON 数组保存。当前 P1 状态机由服务层校验：

```python
open: {in_progress}
in_progress: {open, pending_validation}
pending_validation: {in_progress, closed}
closed: set()
```

后续应将状态变更单独写入 `pc_issue_history`，记录变更前后状态、操作者、原因和时间，形成完整审计轨迹。

## 4. 数据模型

### 4.1 `pc_dataset_import`

保存导入任务和不可变数据集版本：`dataset_version`、`source_filename`、`file_sha256`、`storage_path`、字段映射、质量规则、拒绝原因和行数统计。

关键约束：`dataset_version` 唯一；文件指纹建索引；状态默认 `validated`。

### 4.2 `pc_review`

保存规范化评论：数据集版本、评论 ID、商品、类目、文本、时间、渠道、评分和产品版本。

关键约束：`(dataset_version, review_id)` 唯一。所有来源查询都必须使用复合身份，不能只按 `review_id` 查询。

### 4.3 `pc_review_task`

保存抽样任务、系统预测和人工结论。系统字段与人工字段分开，便于分析模型与人工的分歧。`system_aspects_json` 和 `reviewer_aspects_json` 采用 JSON 文本保存，一期便于兼容现有表结构，P2 可拆为关联表以支持属性统计。

### 4.4 `pc_analysis_run`

保存一次训练/评测或分析运行。`metrics_json` 保存可变指标和训练服务返回内容，主表保存状态和时间。P4 应把核心指标拆成结构化字段，JSON 作为扩展信息，以便排序、筛选和统计。

### 4.5 `pc_issue`

保存问题卡和来源证据。`source_review_ids_json` 当前适合 P1 演示；当支持大量评论、多次验证和评论级引用时，应新增 `pc_issue_review` 关联表和 `pc_issue_history` 历史表。

## 5. API 设计

业务 API 前缀：`/api/v1`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/datasets/imports` | 上传并校验 CSV |
| GET | `/datasets` | 查询最近数据集 |
| POST | `/demo/bootstrap` | 幂等初始化合成数据 |
| GET | `/review-tasks` | 按状态/版本查询审核任务 |
| PATCH | `/review-tasks/{task_id}` | 保存人工审核结果 |
| POST | `/analysis-runs` | 创建人工审核训练运行 |
| GET | `/analysis-runs` | 查询训练运行 |
| POST | `/analysis-runs/{run_id}/sync` | 同步 NLP 任务状态 |
| POST | `/issues` | 创建问题卡 |
| GET | `/issues` | 按版本/状态查询问题卡 |
| PATCH | `/issues/{issue_id}` | 推进问题卡状态 |

接口设计原则：

- 后端校验所有枚举和长度；
- 错误响应包含业务可读信息和 HTTP 状态码；
- 上传接口限制文件类型和大小；
- 训练和问题卡都必须绑定版本；
- 不返回密码、签名密钥或未授权原文；
- 长任务返回任务 ID，不在请求线程等待训练完成。

## 6. 权限与审计设计

P1 使用 JeecgBoot 现有认证和 `get_current_user` 依赖。领域 API 先验证登录，再按角色扩展数据范围。

目标权限模型：

```text
用户 -> 角色 -> 操作权限
用户 -> 组织/团队 -> 数据范围
数据集/评论/问题卡 -> 所属团队与数据密级
```

至少审计以下动作：导入、审核、训练创建、训练同步、模型发布、问题卡状态变更、导出。审计记录应包含用户、对象 ID、版本、动作、时间、结果和失败原因，不记录密码和敏感令牌。

## 7. 存储、缓存与任务设计

### 7.1 文件存储

P1 使用本地版本目录：

```text
runtime/pulsecart/
  imports/<dataset_version>/report.json
  imports/<dataset_version>/records.jsonl
  imports/<dataset_version>/rejected.json
  raw/<file_sha256>.csv
```

P4 迁移到 MinIO/S3。MySQL 只保存对象路径、指纹和状态，不把大文件内容塞入业务表。

### 7.2 Redis 和 worker

导入、批量推理和训练编排未来使用 Redis 队列。任务状态以 MySQL 为最终事实，Redis 只做队列和短期进度缓存；worker 重试必须带幂等键，避免重复导入和重复分析。

### 7.3 训练任务

一次训练运行不能修改另一运行的产物。产物目录应包含模型版本、数据集版本、随机种子、指标 JSON、模型文件和 SHA-256。发布切换应记录旧版本作为回滚目标。

## 8. 错误处理与可观测性

错误分为四类：参数错误、数据质量错误、依赖错误、业务状态冲突。前端应展示可行动的提示，后端日志记录请求 ID、运行 ID、数据集版本和依赖响应，不打印凭据和完整敏感文本。

建议指标：

- CSV 导入耗时、有效率和拒绝率；
- 审核完成量、分歧率和复核覆盖率；
- 训练排队时长、训练时长和失败率；
- 模型 Macro-F1、各类召回率和置信度分布；
- 问题卡从创建到关闭的时长；
- API p50/p95 延迟和依赖错误率。

当前不得填写未实际测得的吞吐量、并发量或生产 SLA。

## 9. 测试策略

### 单元测试

- CSV 字段映射和质量规则；
- dataset version 和 SHA-256 稳定性；
- 重复导入幂等；
- 人工标签过滤和训练记录构建；
- 问题卡状态机；
- 训练服务响应校验。

### 集成测试

- FastAPI + MySQL 领域表；
- 登录后访问控制；
- 业务后端到 NLP 服务的提交和同步；
- 问题卡来源评论版本校验；
- 前端生产构建和关键页面加载。

### 回归测试

- 固定演示数据端到端流程；
- 模型指标和产物指纹；
- 旧模型回滚；
- 真实接入后对不同商品、渠道和版本的聚合结果。

## 10. 部署拓扑

本地开发建议：

```text
浏览器 -> Vue :3100 -> FastAPI :8006 -> MySQL :3306
                                      -> NLP :8100
                                      -> Redis/MinIO（按需）
```

目标 staging/生产拓扑：

```text
反向代理 / SSO
      -> Vue 静态资源
      -> FastAPI API 实例 x N
           -> MySQL 主库/只读副本
           -> Redis 集群 + worker
           -> MinIO/S3
           -> NLP 服务实例 x N
```

NLP 服务和 API 可以独立扩缩容。模型服务不可用时，系统应停止产生新的伪造分析结果；已经落库的历史结果仍可回查。

## 11. 设计风险与后续改进

| 风险 | 当前处理 | 后续改进 |
| --- | --- | --- |
| 人工样本太少 | 训练最低 15 条，发布需更高门槛 | 建立稳定标注集和独立测试集 |
| JSON 字段难统计 | P1 保持兼容 | 属性、指标、历史拆表 |
| 同步接口不适合长任务 | P1 训练服务异步、后端手动 sync | Redis worker + SSE/轮询 |
| 本地文件不适合多实例 | P1 仅本地演示 | MinIO/S3 和对象生命周期策略 |
| 历史模型代码缺少完整权重 | 保留为实验资产 | 补齐训练脚本、产物和基准 |
| 领域权限较粗 | P1 依赖登录 | 按团队、数据密级和角色收敛 |
