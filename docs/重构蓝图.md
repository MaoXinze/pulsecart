# PulseCart 商品体验洞察平台重构蓝图

> 版本：0.1（重构基线）  
> 产品名称：**PulseCart - 商品体验洞察平台**  
> 目标：从“评论情感分析课程项目”重构为帮助商品运营和品类负责人发现体验问题、验证改进效果的分析产品。

## 1. 业务背景与用户

电商、零售和品牌团队每天获得大量评论，但评论往往只被当作文本存档：运营无法迅速发现物流、尺寸、质量、售后等问题何时恶化，也难以证明一次商品或服务改版是否改善了用户体验。简单的“好评/差评”不能支持行动。

| 用户 | 想完成的事 | 产品输出 |
| --- | --- | --- |
| 商品运营 | 判断一个 SKU/类目本周最需要解决的问题 | 主题、属性、情感、样例评论和环比变化 |
| 品类负责人 | 比较商品/版本/渠道的体验差异 | 可筛选的体验指标和问题排行 |
| 数据分析师 | 验证数据和模型是否可靠 | 数据质量报告、模型版本、抽样复核与导出 |
| 客服负责人 | 识别需要优先处理的集中投诉 | 告警、负面趋势和可回查评论 |

产品不采集真实用户身份信息，不替代人工客服，也不将情感标签视为真实评分。它的职责是给出可验证的体验信号和原始样例，协助人做决策。

## 2. 当前审计结论与重构边界

根目录下 `sentiment-plus/` 和 `product-sentiment-plus/` 是同一项目的两个演进版本，不应继续作为两个简历项目：

| 现有部分 | 状态 | 重构决策 |
| --- | --- | --- |
| `sentiment-plus/jeecgboot-vue3` | 含完整后台脚手架，评论页可复用 | 保留 Vue 3、图表和认证能力；逐步删除与业务无关的后台模块 |
| `sentiment-plus/jeecg-fastapi` | 有评论接口、Mock 降级和数据库入口 | 以领域 API 取代 `sentiment_ai_client.py` 的静态 Mock |
| `sentiment-ai-1.0` | 仅二分类推理入口；权重和多数 pipeline 缺失 | 改为可复跑的离线训练/评测/发布链路 |
| `sentiment-ai-2.0` | 多标签路线图和空骨架 | 暂不独立部署；先通过属性/主题标签实现可用洞察 |
| `product-sentiment-plus/` | 初始化版本，数据样例和页面与旧仓高度重叠 | 冻结为归档参考，不新增功能，也不删除 |
| 团队成员、答辩、PPT、待定分工 | 强烈课程项目痕迹 | 从产品 README、界面和文档中移除，改为业务角色和产品验收 |

结论：项目不缺一个 BERT 文件，而是缺少真实数据进入、质量校验、可复跑分析、业务指标、人工复核和模型版本管理的完整闭环。

## 3. 产品范围

### 3.1 MVP 闭环

1. 分析师上传或导入合规 CSV，系统校验字段、重复、语言、日期、评分和空文本。
2. 系统执行标准化、情感/主题/属性预测，保存每条预测对应的数据集和模型版本。
3. 运营按商品、类目、渠道、时间窗口过滤体验看板，找到负面增长最快的属性和代表性评论。
4. 用户在洞察页查看问题证据、编辑业务标签、创建关注项并导出结果。
5. 分析师基于标注样本查看模型混淆、覆盖率、漂移和人工复核结果，再决定是否发布模型。

### 3.2 人工审核和评测闭环

P1 使用约 1,200 条合成扫地机器人评论演示完整业务流，但不将合成数据上的指标表述为电商泛化能力。系统生成 300 条固定审核任务，其中 150 条来自低置信度、负面预测或高风险属性（可靠性、售后、导航避障），其余 150 条按 SKU、产品版本、渠道、月份和情感类别分层随机抽样。

商品运营在审核队列中确认或修正 `positive`、`neutral`、`negative` 情感标签，可多选受控体验属性，并可标记无效文本；不改写原评论。数据分析师对审核完成样本的 10% 做二次复核，分歧必须被保留并进入质量报告。审核集与合成演示数据、未来授权真实数据严格分层，模型评测必须声明使用的数据层和样本规模。

### 3.3 一期模块

| 模块 | MVP 交付 | 明确不做 |
| --- | --- | --- |
| 数据集 | CSV 上传、字段映射、校验报告、导入历史 | 直接抓取电商平台、存储个人信息 |
| 评论分析 | 情感、属性、关键词/主题、置信度、模型版本 | 用硬编码关键词伪造“AI 结果” |
| 体验看板 | 总览、趋势、属性热力图、SKU/类目比较 | 只展示无来源的静态图表 |
| 问题洞察 | 负面主题排行、代表评论、过滤和导出 | 自动替运营下结论 |
| 模型与质量 | 训练运行、指标、抽样复核、发布状态 | 没有训练数据仍声称 BERT 效果 |
| 关注项 | 阈值告警、状态、负责人、备注 | 实时爬虫和自动外部通知 |

## 4. 目标架构

```text
Vue 3 operations console
    | REST / Server-Sent Events for long imports
FastAPI domain API
    |-- Dataset intake + validation
    |-- Analysis orchestration
    |-- Insight aggregation + alert rules
    |-- Model registry + evaluation records
    |-- Auth, roles and audit log
    |
    +-- MySQL: datasets, reviews, predictions, aggregates, alerts, feedback
    +-- Object storage/MinIO: uploaded files and model artifacts
    +-- Redis + worker: asynchronous imports and batch analysis
    +-- NLP model service: preprocess, train, evaluate and batch inference
          |-- TF-IDF + Logistic Regression / Linear SVC baseline
          |-- Transformer fine-tuning experiments (BERT/RoBERTa)
          |-- model registry, release switching and health checks
          +-- compression / quantization benchmark records
```

后端以业务领域划分：`datasets`、`reviews`、`analysis`、`insights`、`issues`、`models`、`auth`。业务 API 只负责编排、权限、审计和数据落库；模型服务独立维护模型加载、训练、评测与推理，且不直接访问 Web 请求对象。API 不直接写模型文件；前端不直接计算指标。长文件导入和批量推理由 Redis worker 执行，任务以状态机追踪。训练、批量推理和模型切换均可独立扩缩容，不能阻塞运营端请求。

## 5. 数据契约、分析策略和模型治理

### 输入数据契约

最小字段为 `review_id`、`product_id`、`review_text`、`reviewed_at`；推荐字段包括 `category_id`、`channel`、`rating`、`product_version`。导入时生成不可变 `dataset_version`，原始文件保存校验和，输出清洗记录及拒绝行原因。

当前 P1 已提供不依赖外部服务的导入实现：`sentiment-ai/app/services/dataset_import.py`。它支持 UTF-8 CSV、标准字段和常见别名、显式字段映射、ISO 日期、1-5 评分、字符级语言标记、重复 `review_id` 拒绝、重复文本质量提示和拒绝行报告。结果落在 `data/imports/<dataset_version>/`，包含 `report.json`、`records.jsonl` 和 `rejected.json`；同一文件字节内容与同一字段映射跨进程重复导入时复用已有版本。

本地演示命令：

```powershell
cd sentiment-ai
python scripts/import_reviews.py data/demo/reviews_sample.csv
```

该命令只使用 Python 标准库；真实部署时，版本目录应由对象存储和数据库任务记录接管，仓库只保留 `data/demo` 中的合成数据。

保留三层数据：

| 层 | 内容 | 可否提交 Git |
| --- | --- | --- |
| `data/demo` | 合成或明确可再分发的小样本 | 可以，必须写来源和许可 |
| `data/raw` | 原始客户/公开数据下载件 | 不可以，使用 `.gitignore` |
| MySQL / MinIO | 导入版本、预测、聚合、产物 | 不可以，以迁移和种子脚本复现 |

### 分析策略

先将可信、可复现置于“模型数量”之前：

1. 文本清洗、语言识别、去重和字段质量报告是所有下游分析的前置条件。
2. 使用 TF-IDF + Logistic Regression 或 Linear SVC 建立可解释的情感基线，保存划分、随机种子、阈值和完整指标。
3. 有足够授权标注数据时再训练中文 Transformer；若未满足数据量和显著性要求，BERT 保持实验状态，不能成为默认线上模型，默认分析仍使用可解释的基线。
4. 已验证的 Transformer 在 P1 仅采用动态 INT8 量化，并记录压缩前后体积、CPU 推理延迟、吞吐量和评测集 F1；无实测报告不得宣称“模型压缩成功”。
5. 知识蒸馏到小模型属于 P2，只在有足够人工审核样本和明确教师模型基准后开展，防止用合成数据制造不可信的结论。
6. 属性采用受控词表加人工审核起步，主题采用可追踪的聚类/关键词方法；每项洞察必须链接到原始评论和模型/规则版本。
7. 模型服务提供健康检查、批量推理、模型版本切换与延迟记录；业务 API 调用它时必须传入指定的 `model_version`，禁止隐式使用“最新模型”。
8. 模型发布必须记录 `model_version`、训练数据版本、代码版本、指标、审核人、发布时间、回滚目标，以及压缩/量化方式和对应基准结果。

## 6. 数据模型与 API

核心表：`datasets`、`dataset_imports`、`reviews`、`analysis_runs`、`review_predictions`、`aspect_taxonomy`、`insight_snapshots`、`alert_rules`、`alerts`、`model_versions`、`evaluation_runs`、`review_feedback`、`audit_logs`。

关键 API 采用 `/api/v1` 前缀：

| 功能 | 接口示例 | 可验证结果 |
| --- | --- | --- |
| 创建导入 | `POST /datasets/imports` | 返回任务 ID 和字段映射校验 |
| 查看任务 | `GET /imports/{id}` | 行数、拒绝原因、状态、耗时 |
| 发起分析 | `POST /analysis-runs` | 固定 dataset/model/version 参数 |
| 查看看板 | `GET /insights/overview` | 数据窗口、筛选条件和聚合版本 |
| 查看证据 | `GET /insights/aspects/{id}/reviews` | 原文、预测、置信度和来源版本 |
| 模型评估 | `GET /models/{id}/evaluations` | 划分、指标、混淆矩阵、复核结果 |
| 设置告警 | `POST /alert-rules` | 规则、阈值、作用范围和状态 |

所有聚合 API 必须返回数据时间窗口、数据集版本、模型版本和筛选条件，以避免图表“看似正确但不可追溯”。

## 7. 环境、测试和部署基线

| 项目 | 固定选择 | 原因 |
| --- | --- | --- |
| Python | **3.12.x** | ML 依赖和 FastAPI 的稳定兼容基线 |
| Node.js | 22 LTS + pnpm | 前端构建与质量检查 |
| MySQL | 8 | 复用现有后端的关系数据和迁移基础 |
| Redis | 7 | 导入/分析任务队列和短状态 |
| 对象存储 | MinIO 本地、S3 兼容生产 | 原始附件和模型产物分离 |
| 容器 | Docker Compose | 本地一键启动依赖、staging 可迁移 |

当前宿主机只有 Python 3.14、Node 22 和 pnpm，没有虚拟环境、Python 测试工具或前端依赖；因此后续会在仓库提供 Python 3.12 的锁定依赖、`.env.example`、Compose、数据库迁移、种子数据和单命令质量检查，不将本机安装状态视为项目环境。

发布前必须执行：数据契约测试、导入幂等性测试、聚合正确性测试、模型评测回归、权限/API 集成测试、前端构建、容器健康检查和一组固定 Demo 数据的端到端测试。模型指标、运行时间和吞吐量只记录实测值。

## 8. 实施路线

| 阶段 | 交付 | 完成定义 |
| --- | --- | --- |
| P0 基线 | 本文、去课程化 README、环境和数据协议 | 新成员能理解产品和数据边界 |

| P4 工程交付 | Docker、测试、演示数据、部署文档 | 其他人可独立启动并演示 |

## 9. 简历表达边界

达到 P2/P3 后，可用如下模板，并仅替换为真实、可复现的结果：

> PulseCart｜商品体验洞察平台｜个人/核心开发  
> 面向商品运营场景，使用 Vue 3、FastAPI、MySQL 8、Redis 构建评论数据导入、质量校验、版本化分析和体验洞察闭环；实现情感基线/模型版本管理、属性趋势聚合、可回查评论证据和规则告警。基于 [数据集版本] 完成 [评测集规模] 的可复现实验，实测 [F1/导入耗时/接口延迟]。

不要写“BERT 准确率 92%”“海量评论实时分析”或“生产上线”等未由训练产物、监控报告和部署记录证明的内容。原项目的通用 Jeecg 后台、成员分工文档和静态 Mock 不能单独作为产品成果。
